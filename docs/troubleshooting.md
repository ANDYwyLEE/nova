## Reading the log

Start with `./nova doctor` (Windows: `nova doctor`): one screen with the versions, the FFmpeg build inside PyAV, the OpenGL driver, hardware decoders, GPUs, audio devices, a masked summary of `cameras.ini`, the last warnings in the logs and a few verdicts (software OpenGL, an NVIDIA driver too old for the wheel's NVENC, a readable `cameras.ini`, low disk space). It is the first thing a bug report should contain.

Run one camera in the foreground with `-l DEBUG` (`./nova run ID -l DEBUG`) and read the lines in this order: `[VideoWorker] av.open(…)` (connection), `HW decoder:` / `software decoder` (decoder choice), `First frame (…)` (pixel format and size), then `[AVWriter]` lines when recording or streaming starts. Passwords are masked in all log output, so logs can be shared.

## Connection and decoding

| Message | Meaning | What to do |
|---|---|---|
| `Unreachable: host:port …` or `Failed: Connection timed out` (overlay) | camera down or unreachable | check IP/port, firewall; Nova retries every 10 s; `NOVA_TIMEOUT` sets the socket timeout |
| `Failed: 401 Unauthorized` / `Invalid data found` | wrong credentials or wrong path | let Nova find the path: `onvif://user:pw@ip`, or the brand shortcut (`hik://`, `dahua://`, `reolink://`, …: [Camera brands](user-guide.md#camera-brands)) |
| `ImportError: libgthread-2.0.so.0` (or `libglib-2.0.so.0`, `libEGL.so.1`, `libgssapi_krb5.so.2`, …) when a camera starts; cameras that `exited right after start` | a system library Qt loads is not installed: a minimal system, a container, another distribution's package split | install the packages of your distribution's line in [install.md](install.md#linux); `nova doctor` names the Qt module that does not load and the library it misses |
| `No matching distribution found for av>=19.0.2` during `pip install`; `nova: the venv here was made with Python 3.N, and Nova needs Python 3.12 or newer` | the venv was made with the distribution's own Python, which is older than 3.12 (Debian 12: 3.11, Ubuntu 22.04: 3.10) | make the venv with a newer Python: [install.md](install.md#linux), *Debian 12, Ubuntu 22.04, Linux Mint 21* |
| `No matching distribution found for PySide6==6.12.0` during `pip install` | a C library older than glibc 2.34 (Debian 11, Ubuntu 20.04, RHEL 8): PySide6 has no wheel for it from 6.10 on | PySide6 6.9.3: [install.md](install.md#linux), *Older systems* |
| `ID: was ended by SIGILL (illegal instruction: …) right after start` from `nova start`; `Illegal instruction` after `python nova.py …`; nothing in the camera's log | a Python package was built for a newer CPU than this one: the numpy wheels from 2.4 on need SSE4.2 | `nova doctor` names the package (`CPU … no SSE4.2`, and a line under Checks); `pip install "numpy<2.4"`: [install.md](install.md#linux), *A CPU without SSE4.2* |
| `--accel=X is not supported by this FFmpeg/PyAV build` | the wheel lacks that hwaccel (e.g. `vaapi`) | use `cuda`/`qsv`/`d3d11va`, or build FFmpeg ([custom-ffmpeg.md](custom-ffmpeg.md)) |
| the same line after building FFmpeg yourself | the venv still holds the `av` wheel: `pip install --no-binary av av` answered `Requirement already satisfied` | `pip install --force-reinstall --no-binary av av --no-cache-dir` ([custom-ffmpeg.md](custom-ffmpeg.md)) |
| `No working HW decoder for --accel=qsv (…)` on Linux, `Error creating a MFX session` with `-l DEBUG` | Intel's Quick Sync runtime or its VA driver is not installed | Ubuntu and Debian: `sudo apt install intel-media-va-driver-non-free libmfx-gen1.2`; Fedora, openSUSE and Arch have other names ([install.md](install.md#linux)); `nova doctor` says whether Quick Sync starts and names the packages |
| `Failed to initialise VAAPI connection`, then `No working HW decoder for --accel=vaapi` | `--gpu` / `NOVA_GPU_DEVICES` points VAAPI at a GPU without it: GPU N is `/dev/dri/renderD(128+N)`, and on a machine with NVIDIA cards only the Intel or AMD GPU's node answers | `nova doctor` lists the GPU behind each node; give the camera that one, or no `--gpu` at all: Nova then takes the first node that is not an NVIDIA card |
| `No VA display found for device /dev/dri/renderD…`, then `No working HW decoder for --accel=vaapi` (Quick Sync: `Unknown error occurred`) | the user may not open the GPU's render node: no desktop login (ssh, a service, a container) and not in the node's group | `sudo usermod -aG render $USER`, then log in again; `nova doctor` says `… is closed to USER` |
| `GPU N (--gpu / NOVA_GPU_DEVICES) does not open on this machine; using GPU 0` / `h264_nvenc does not open on GPU N (…); trying GPU 0` | the index names an NVIDIA card this machine does not have (a `cameras.ini` from a machine with more cards) | nothing breaks: the camera runs on GPU 0. Correct `NOVA_GPU_DEVICES` or `--gpu` to the cards `nvidia-smi` lists |
| `No working HW decoder for --accel=cuda (reason). Falling back to software (codec); hardware is tried again in N min` | the hardware decoder cannot be used: wrong `--gpu`, GPU out of memory, or a stream it cannot decode (rawvideo webcams, MJPEG 4:2:2, an unusual profile) | the picture continues in software without reconnecting; hardware is tried again after 5, 10, 20, 40, then every 60 min. Check `nvidia-smi` and `--gpu` / `NOVA_GPU_DEVICES` if it keeps happening |
| `Reconnecting: no audio for N s while video keeps flowing`, or `… for 5 s since the video timestamps went back N s …` | the camera stopped sending the audio of this connection and sends it again to a new one. With `since the video timestamps went back`: the camera's clock started again, which one make of camera does every 3 h 18 min 50 s after it was switched on (a 32-bit count of 1/360000 s) | Nova reconnects by itself while the sound is played, recorded or streamed; the picture pauses for a few seconds. `NOVA_AUDIO_STALL` (seconds, `0` = never) in `[env]` changes the wait. For the 3 h 18 min kind only new firmware for the camera would help; Nova keeps the silence to about 11 s |
| `the source's timestamps step back and forth while its stream goes on` | the camera's RTCP sender reports do not fit its RTP timestamps, so its timestamps step by up to seconds every few seconds (seen with four cameras of one make) | nothing to do: Nova no longer writes those steps as gaps ([Recording](recording.md#timestamps-and-av-sync)). Recordings made before that are longer than the time they cover and have holes in the sound |
| `the picture was gone for N s on this connection and is back (M video packets came in that time, the longest wait for one was X s)`, `the sound was gone for N s on this connection and is back` (at `-l INFO`) | the camera sent no picture, or no sound, for more than 5 s and went on by itself before a watchdog was due (10 s without video, 30 s without audio) | nothing to do: it explains a gap in a recording. X near N: the camera sent no video at all; many packets and a small X: it sent video that no picture could be made of |
| `Reconnecting: no video for N s while audio keeps flowing` / `no picture for N s` / `N video packets in a row failed to decode` | the camera's video stalled or is broken while the connection stays up (single damaged packets are skipped) | Nova reconnects by itself; repeated: lower the camera's bitrate or check its network |
| `a picture takes N ms here and the camera sends one every M ms: the decoder gets K threads from now on (the picture is K-1 frame(s) later for it); reconnecting` | the software decoder works on one thread, and that did not keep up with this camera (an old or small CPU; a 4K or high-bitrate stream). Until then the camera's packets piled up, and it dropped some (`RTP: bad cseq`, `error while decoding MB …`) and then the connection (`Failed reading RTSP data: End of file`, `stream ended after N s`), every few seconds | nothing: the connection comes back decoding on K threads, and `First frame (h264, SW, K threads)` says so; it is asked again, with twice as many, if that is still too few. `--ffmpeg "-thread_type frame -threads N"` sets the threads by hand, and Nova then leaves them alone |
| `⚠️ this CPU does not keep up with the camera: a picture takes N ms here on K threads and the camera sends one every M ms. What needs less: …` (once) | every core decodes already, or `--ffmpeg` names the threads, and it is not enough: the picture stutters and the connection keeps ending | what the line lists: the camera's second, smaller stream (`hik://…/sub`, or its own RTSP path), a lower resolution, frame rate or bitrate set in the camera, a GPU decoder (`--accel`), `--opengl` (no conversion of each picture), `--ffmpeg "-skip_frame nokey"`; or fewer cameras on this machine |
| `cannot read host:port from the URL … must be percent-encoded (%2F %3F %23 %40 %5B %5D)` | the password contains `/ ? # @ [ ]` unencoded | write those characters percent-encoded in `cameras.ini` (`pa/ss` → `pa%2Fss`) |
| `non-existing PPS 0 referenced` / `no frame!` (once) | joined the stream mid-GOP | normal; decoding starts at the next keyframe |
| `Stream error:` in the window, `[VideoWorker] Stream exception:` in the log, every few seconds | the camera drops the connection | try `--ffmpeg "-rtsp_transport udp"` (or `tcp` if you set udp); lower the camera's bitrate |
| `Failed: URI resolve` in the window, `[ONVIF] ❌ All attempts failed for IP`, `[Hikvision] ❌ …`, `[Reolink] ❌ login refused …` in the log | discovery failed: management port not found, credentials rejected, no such channel or stream | give the management port explicitly (`onvif://user:pw@ip:8080`, `hik://user:pw@ip:8080`), check the `/CHANNEL/STREAM` part (the log lists the streams a recorder has), run with `-l DEBUG` (`-l TRACE` adds the SOAP bodies) |
| `⚠️ RTSP is switched off on IP` / `the RTSP server is switched off` (Hikvision, Reolink, XMeye) | the device's RTSP server is disabled | turn it on in the device's settings (the log names the menu); the URL is right but the connection fails until then |
| `[Reolink] ⚠️ HTTPS is switched off on IP: the password went over plain HTTP` | the camera offers HTTP only | enable HTTPS in the Reolink app (Network > Advanced > Port Settings); Nova tries it first |
| `cannot parse the hik:// URI; expected …` | the shortcut is not `scheme://user:password@host[:port][/CHANNEL][/STREAM]` | `STREAM` is `0`/`main`, `1`/`sub` or `2`/`third`; a `:` in the user name is written `%3A` |
| `Connection refused` from a recorder's RTSP port right after many channels were started, for about a minute | XMeye recorders stop accepting RTSP connections after a burst of them (measured: 17 sessions within a minute, refused for 90 s) | keep `stagger` in `cameras.ini` (0.5 s or more) when several windows point at one recorder; wait a minute before retrying |
| no picture through a recorder channel, `non-existing PPS 0 referenced` repeated in the log | the parameter sets the recorder relays for that camera are not accepted by FFmpeg's decoder | open that camera directly by its own address instead of through the recorder |
| decoder `ignored unknown --ffmpeg options: {…}` | no decoder has an option of that name (a typo?) | options of *other* decoders (`-resize` is cuvid's) are left out quietly for the one in use; `-skip_frame` is accepted by cuvid but has no effect there; see [ffmpeg-options.md](ffmpeg-options.md) |
| `--ffmpeg -x is an option of the ffmpeg program, not of the FFmpeg libraries` at start | `-t`, `-map`, `-re`, `-fps_mode`, `-q`, … exist in the `ffmpeg` executable only | the message names Nova's equivalent when there is one (`--record-interval`, `-r N`, `-crf`/`-cq`) |

## Display

| Symptom | Cause | Fix |
|---|---|---|
| black window, log says `Shader Error` or `initializeGL Error` | no OpenGL 3.3 core context (remote desktop, old GPU, some VMs) | drop `--opengl` (QPainter renderer) or install a Mesa with llvmpipe |
| GNOME / KDE / Xfce: windows open centred or stacked top left, keyboard moves do nothing | native Wayland window (`QT_QPA_PLATFORM = wayland` in `[env]`), or an older Nova in a session that exports `QT_QPA_PLATFORM=wayland` (Xfce's Wayland session does): the compositor ignores client-side positioning | drop that setting / update (Nova then uses XWayland, where GNOME, KDE and labwc honour positions), or on KDE import rules from `nova layout export NAME kwin` (user guide, Layouts) |
| Xfce (Wayland) session returns to the login screen at once | the `labwc` compositor it runs on is not installed | `sudo apt install labwc`; with several GPUs set `WLR_DRM_DEVICES` in `~/.config/xfce4/labwc/environment` to the one driving the monitor |
| sway / Hyprland: windows tiled or centred, keyboard moves do nothing | an older Nova, or `NOVA_WM_IPC = 0`: these compositors ignore the positions windows ask for | update (Nova places its windows through the compositor's IPC), or import rules from `nova layout export NAME sway` / `hyprlang` |
| Cinnamon on Wayland (experimental session): a black screen with only the cursor after login | Xwayland 24.1.10, the version in Ubuntu 26.04, crashes when the first X11 program draws (fixed upstream in 24.1.11); Cinnamon restarts twice and gives up | install Xwayland 24.1.11 or later; to get the login screen back, from a text console: `loginctl terminate-session N` and end the leftover `cinnamon-session-binary` |
| every camera exits right after `nova start` on a Wayland login ("exited with code 0", or `OpenGL could not be initialised … no valid context` in logs/ID.log) | an older Nova: PyOpenGL picks EGL from `XDG_SESSION_TYPE=wayland` while the XWayland window's context is GLX (fixed 2026-11-08) | update, or set `PYOPENGL_PLATFORM = glx` in `[env]` |
| window exists but shows nothing (native Wayland, NVIDIA, `--opengl`) | an older Nova: the OpenGL draw buffer was left at `GL_NONE` (fixed 2026-10-13) | update, or run under XWayland: drop `QT_QPA_PLATFORM` from `[env]` (the default) |
| colours slightly off (greenish skin tones) | camera signals no colour space | Nova assumes BT.709 above 576 lines, BT.601 below; cameras that lie cannot be helped without `-vf colorspace=…` |
| high CPU with `--opengl` and `--accel cuda` | the stream is not H.264/HEVC (MJPEG cameras decode in software) | `-f 10`; or `--ffmpeg "-skip_frame nokey"` for a cheap preview of a camera you do not record (recordings and streams get the same one frame per GOP) |
| the window is huge on a 4K camera | windows default to the saved geometry, first run uses 320×180 | **Home** gives 1:1, right-click fits, **PgUp** shrinks |
| control strip never appears | the mouse must enter the top-left corner of the *video area* (not the letterbox) | press **H** instead, or widen the window |

## Recording and streaming

| Message | Meaning | What to do |
|---|---|---|
| `[AVRecorder] recording failed: …` then `[AVRecorder] restarting in N s` | the encoder or the disk failed | the message says which (`No space left`, `Permission denied`, an encoder error); recording starts again by itself (5, 10, 20, 40 s, then every 60 s) once the cause is gone |
| `[VideoWorker] recorder cannot keep up: N frame(s) dropped` (`streamer cannot keep up`), every 10 s | the encoder is slower than the camera: `libx264` at its default preset on a slow CPU or at 4K, a GPU encoder that was answered with `libx264`, a disk or an uplink that stalls. The frames it names are missing in the recording | a faster preset, `--ffmpeg "-preset ultrafast"` (an Atom D525 of 2010 records 1080p at 10 fps with it and 2 to 6 of the 10 frames without); a GPU encoder (`--accel`, `-e`); the camera's second, smaller stream |
| `[AVRecorder] not recording: … another Nova process (pid N) …` | a second Nova runs the same camera and its recorder holds the folder | stop one of them (`nova status`, `ps`); this one takes over within a minute after the other stops |
| `segment left by a crash kept: …_recovered.mp4` | the previous run was killed (power loss, OOM, `kill -9`) mid-segment | nothing: the file plays up to its last fragment |
| `cannot rename … it keeps its name, the next segment is written next to it` | the finished segment could not be renamed (permissions, a file locked by a player on Windows) | the rename is tried again later; the file is complete under its temporary name |
| `No quality level set; using default (20)` (VAAPI) | FFmpeg's note that no bitrate or quality was asked for: constant quality, the size follows the scene | nothing if the sizes suit you; else `--ffmpeg "-b:v 2M"` |
| `Using the constant quantization parameter (CQP) by default` (Quick Sync) | FFmpeg's note that no bitrate or quality was asked for: the quality is constant and the file size follows the scene | nothing if the sizes suit you; else `--ffmpeg "-b:v 2M"` or `-global_quality 28` ([recording.md](recording.md#quick-sync-how-large-the-files-get)) |
| `⚠️ -e NAME does not open here (…); using OTHER` | the encoder asked for with `-e` cannot start on this machine: no such GPU or driver, a build without it, or a codec the GPU cannot encode (`av1_qsv` and `av1_vaapi` on a UHD 620 or UHD 770) | drop `-e` or name one that works; the line says which encoder records instead |
| `Driver does not support the required nvenc API version` (at `-l DEBUG`), recordings by `libx264` | a self-built FFmpeg whose NVENC headers are newer than the NVIDIA driver | rebuild with the headers release that matches the driver ([custom-ffmpeg.md](custom-ffmpeg.md#linux-ubuntu-2604-nvidia--srt--vaapi)) or update the driver |
| `⚠️ h264_nvenc does not open at WxH (…); using libx264` | the probe passed but the real size did not open (NVENC session limit with many cameras, a GPU fault) | nothing to do; the encoder is tried again after an hour. Fewer NVENC sessions: record some cameras with `-e libx264` |
| `⚠️ -e hevc_nvenc: flv carries h264 only` | the forced encoder's codec does not fit the target (RTMP is H.264) | drop `-e` for that camera, or use HLS for HEVC |
| `audio encoder … does not open at N Hz …; no audio track` | the camera's audio format cannot be encoded as set (`-ar`/`-ac`) | change or drop `-ar`/`-ac`; video is unaffected |
| `EncoderManager ⚠️ h264_nvenc rejects your --ffmpeg options {…}` | option names differ per encoder | NVENC: `-preset p1…p7 -tune hq/ll/ull -cq N`; libx264: `-preset ultrafast…veryslow -crf N -tune zerolatency` |
| `video encoder … ignored unknown --ffmpeg options` | no encoder has an option of that name (a typo?); options of other encoders (`-cq` with libx264) are left out quietly | see the tables in [ffmpeg-options.md](ffmpeg-options.md) |
| `… are ffmpeg command-line options without a library equivalent; ignored` | `-t -ss -map -re -vsync …` only exist in the `ffmpeg` program | use `--record-interval`, `-r`, `-vf` instead |
| `-vf: filter 'drawtext' is not available in this FFmpeg build` | the PyPI wheel has no libfreetype | custom build, or burn text in later with ffmpeg |
| `empty segment discarded` | nothing was written during the segment (no frame arrived, or the file could not be started) | the camera was down, or see the error before it; nothing lost |
| recordings play too fast / audio drifts | fixed in the 2026-10-11 release (timestamps now follow the camera clock) | update |
| YouTube: "no video" | the encoder produced AV1/HEVC for RTMP (old release) or the key is wrong | update; RTMP now always gets H.264, also with `-e hevc_nvenc` set |
| `[AVStreamer] write timed out, giving up` then `reconnecting in N s` | the ingest server or the uplink stopped accepting data for `NOVA_TIMEOUT` | nothing: Nova reconnects by itself (5 s, 10 s, … then every 60 s) while the gray LIVE icon shows; press `T` to stop trying |
| `[AVStreamer] cannot open output: …` repeating | the connection is refused at every attempt: wrong key, server down, DNS, port 1935 blocked | fix the cause; the next attempt (at most a minute later) picks it up |
| `AVStreamer worker stopped: [Errno 5] Input/output error` right after start | the ingest server closed the connection: wrong key or unsupported codec | check the key; for RTMP keep H.264 |

## Audio

| Message | Meaning | What to do |
|---|---|---|
| `[AudioWorker] cannot open an audio output: …` (once; retried every 3 s) / `Audio stream open error` | no usable PortAudio output device, or the sample rate is refused | `NOVA_AUDIO_DEVICE_INDEX=N` (devices are listed with `-l TRACE`); Nova already retries at 48 kHz |
| crackling, drop-outs | the audio thread is starved or the device buffer is small | close other audio apps; on Linux prefer the PipeWire/Pulse device (chosen automatically when present) |
| no sound but the icon is on | the camera stream has no audio track | the window title/log shows `audio=none`; check the camera's audio setting |

## Performance tips

- **One GPU, many cameras**: NVDEC on a single RTX 4090 decodes well over 20 1080p streams; the limit is usually the display rate. `-f 15` halves the upload to the GPU without touching recordings.
- **Two GPUs**: `NOVA_GPU_DEVICES = 0,1` in `[env]`; `nova start` deals the cameras over them in turn and `nova list` shows who gets which. `opts = --gpu 1` pins a camera. `nvidia-smi` lists one process per camera under the GPU it uses.
- **Big cameras, small windows**: `--ffmpeg "-resize 960x540"` (cuvid) scales inside the decoder, so display, recording and streaming all work on the smaller frame.
- **Software decoding**: one thread decodes a camera, and when that does not keep up Nova gives the decoder more by itself and says so in the log ([above](#connection-and-decoding)); `--ffmpeg "-thread_type frame -threads N"` sets them by hand. `--ffmpeg "-threads 2"` per camera avoids 15 processes each spawning 32 threads; `-skip_loop_filter all` trades a little quality for ~20 % CPU; `-skip_frame nokey` shows one frame per GOP almost for free (and records and streams only those frames, so not for a camera you record).
- **Recording cost**: NVENC is nearly free; libx264 `-preset veryfast` or `ultrafast` when there is no hardware encoder.
- **An old or small CPU**: measured on an Atom D525 (2010, two cores with four threads, 1.8 GHz; Debian 11, NVIDIA ION on `nouveau`) with 1080p cameras. A 10 fps camera in a window: 37 % of a core with `--opengl`, 78 % without it. A 25 fps camera at 15 Mbit/s: more than one thread decodes (54 to 58 ms a picture), 220 % of a core on three. Recording the 10 fps camera with `libx264`: 144 % of a core with `-preset ultrafast`, and not possible at the default preset. Four 1080p cameras at once were more than it could do: that is what a camera's second stream is for.
- **Memory of a recording camera**: a camera that only shows its picture keeps its size for days (measured over 40 hours). One that records through Quick Sync grows for a while and then stops: a few MB at a segment change at first, 40 to 55 MB in all, flat after the first 50 to 100 segments, which is one to two days at the default 30 minutes (watched with 10 s segments on two cameras, over 150 and 330 segment changes). It is memory the C library keeps for the threads that used it, not a leak: an encoder opened and closed 200 times stops growing after 50. `MALLOC_ARENA_MAX = 2` in `[env]` keeps such a process at its start size (a 25 fps camera: 217 MB at the start and after 150 segments, 261 MB without it); NVENC recording does not grow at all.
- **A camera that is down**: the window shows `Unreachable: host:port …` and Nova retries every 10 s. The host is probed with a plain TCP connect before the RTSP open, so `nova stop` ends such a camera at once. Only a camera that *answers* but then stalls in the RTSP handshake can hold a stop for up to `NOVA_TIMEOUT` (that open cannot be interrupted earlier).
- **Start-up storms**: `nova start` staggers starts (`stagger = 0.5`) and encoders are probed under a cross-process lock, so 15 cameras can start at once without fighting over the GPU.

## Known limitations

- No PTZ control, motion detection or event recording; Nova is a viewer/recorder.
- One window per process by design; there is no mosaic window (arrange windows on the grid instead).
- Display audio is live, not lip-synced to the picture; recordings and streams are in sync.
- Frame-rate-changing filters (`fps`, `minterpolate`) are not supported in `-vf`; use `-r`.
- SRT and VAAPI need a custom FFmpeg build; `drawtext` needs libfreetype (not in the wheel).
- Quick Sync: `--gpu` does not choose among Intel GPUs; B-frames are off unless you ask (`-bf`); the integrated GPUs it ran on here (UHD 620, UHD 770) have no AV1 encoder; on Linux Intel's runtime covers the 11th generation and newer, an older GPU needs VAAPI instead.
- Windows without a desktop (ssh, a service): recording works with Quick Sync, `d3d11va` and `d3d12va` decoding; `dxva2` needs a desktop session (`Failed to create Direct3D device`).
- Wayland: Nova runs under XWayland by default; GNOME, KDE and Xfce (labwc) then honour its positions, on sway and Hyprland Nova places its windows through the compositor's IPC. wlroots compositors (sway, labwc; Hyprland's Aquamarine likewise) cannot show one desktop on monitors attached to two different NVIDIA GPUs: the copy between them fails (EGL and Vulkan alike); GNOME, KDE and the X11 desktops can.
- Windows capture devices need a device name (`dshow://video=NAME`); numeric ids work on Linux (`0` = `/dev/video0`) and macOS.
